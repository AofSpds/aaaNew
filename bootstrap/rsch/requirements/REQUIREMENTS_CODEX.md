# 도메인 기반 에이전트 작업대와 기억 요구사항

작성: Codex  
갱신: 2026-10-14  
상태: 현재 대화의 사용자 요구와 설계 방향을 정리한 초안. 구현 완료나 제품 채택을 뜻하지 않는다.

## 목적

bootstrap은 도메인을 처음 만드는 프로젝트다. 도메인이 에이전트에 역할·작업대·필요한 기억을 전달하여 업무를 이어가게 하고, 수행 중 쌓인 경험을 다음 업무에 재사용한다. 사용자가 같은 맥락을 반복해서 설명하거나 에이전트가 같은 탐색·실수·구현을 반복하는 비용을 줄이는 것이 목적이다.

## 사용자 요구

### R01 프로젝트와 역할별 작업대

프로젝트가 발의되면 역할에 맞는 작업대를 둔다. 현재 논의한 역할은 rsch와 pln이며, 큰 계획에는 다음 마일스톤을 수행하는 서브 프로젝트와 sub_pln 같은 작업대가 생길 수 있다. rsch를 모든 프로젝트의 상설 역할로 확정하지 않는다.

세션을 열면 해당 역할의 작업 폴더가 실제 작업 위치로 지정되어야 한다. 세션이나 에이전트가 바뀌어도 기존 업무와 기록을 이어받을 수 있어야 한다. 현재 이 조사의 작업대는 C:\Users\ms1pk\dev\aaaNew\bootstrap\rsch다.

### R02 도메인이 시작 시 필요한 기억 전달

기억 전달의 주체는 도메인이다. 에이전트가 업무를 시작할 때 역할, 현재 업무, 작업대 위치와 필요한 경험을 제공한다. 사용자가 매번 파일 위치와 프로젝트 맥락을 다시 설명하는 데 의존하지 않는 방향이다.

첫 모델 호출 전 전달할 수 있는 가장 이른 접점을 조사한다. 도메인을 통해 시작한 세션과 사용자가 외부 앱에서 직접 연 세션을 구분하여 개입 가능한 범위를 확인해야 한다. 파일이 존재하는 것, 모델 입력에 포함된 것, 실제 준수한 것을 따로 확인한다.

### R03 실행 옵션 선택

다음 방식을 선택할 수 있도록 하고 싶다는 사용자 요구다.

- OAuth 인증으로 모델을 직접 연결하고 선택한 실행기가 업무를 수행하는 방식.
- Codex CLI를 실행하는 방식.
- Claude Code CLI를 실행하는 방식.

인증 방식과 실행기 선택은 구분한다. 특정 실행기가 모든 옵션을 이미 지원한다고 가정하지 않는다. 옵션마다 기억 전달·작업대 지정·시작 훅의 접점이 달라도 도메인의 역할과 기억 관리 기준은 유지되어야 한다.

### R04 지침을 넘어 실제 통제 경계 확인

조사는 작성 가이드보다 프로그램이 개입하는 지점을 우선한다. 각 옵션에서 다음을 확인한다.

- 무엇이 언제 기억을 모델 입력에 넣는가.
- 준비가 끝날 때까지 첫 모델 호출을 기다리게 할 수 있는가.
- 전달 실패를 감지하고 업무 실행을 보류할 수 있는가.
- 도구 실행 요청이 어느 실행기를 통과하며 어떤 경로가 통제 밖에 있는가.
- 재개·문맥 압축 이후에도 필요한 기억을 갱신·전달할 수 있는가.

실패 시 반드시 차단할 작업의 범위와 예외 정책은 아직 정하지 않았다. 시작 훅을 설정했다는 사실만으로 전달이나 차단 성공을 판정하지 않는다.

### R05 시행착오를 역할별 경험으로 축적

작업 기록과 사용자 정정, 성공·실패 경험을 보존한다. 이를 리뷰하여 역할별 경험 view를 만들고 다음 업무에서 필요한 내용을 사용할 수 있어야 한다.

일회성 진행 상태와 여러 업무에 재사용할 교훈을 구분해야 한다. 기록량을 늘리는 것보다 다음 업무에서 재설명·재탐색·재작업을 줄이는 데 초점을 둔다.

### R06 jevlike 기반 관계 엔진

사용자 지정 방향은 jevlike 엔진을 기반으로 관계 엔진을 두는 것이다. 해결하려는 문제는 MD 내부와 문서 사이의 불필요한 의미 중복, 내용 충돌, 관계 미정립이다.

기억 항목과 관계를 구조화하여 관리하고, 역할별 MD는 필요한 내용을 보여주는 view로 만드는 방향으로 논의했다. 같은 기억을 여러 문서의 독립 원본으로 복제하여 각각 수정하는 구조를 피한다.

jevlike의 현재 구현이 어떤 요구를 충족하는지는 별도로 확인해야 한다. 특정 DB나 그래프 저장 제품을 선택한 상태가 아니다.

### R07 작업대를 관찰하는 UI

사용자가 코드를 직접 편집하지 않더라도 사이드바 등에서 작업대 파일을 탐색하고, 파일명과 내용을 검색할 수 있기를 원한다. 에이전트가 남긴 기록과 결과를 사용자가 찾아볼 수 있어야 한다.

VS Code·Cursor 같은 기존 UI를 사용할지 별도 앱을 만들지는 미정이다. 모바일에서는 사이드바에 의존하지 않고 핵심 내용을 채팅에서 짧게 한 부분씩 볼 수 있어야 한다.

### R08 요구사항 별도 보관

요구사항은 rsch 아래 별도 requirements 폴더에 보관한다. 작업 기억에는 현재 요구사항 문서의 위치를 연결한다. 사용자 요구, 구현을 위한 제안, 미결정 사항을 구분하여 갱신한다.

## 논의된 설계 후보

아래는 요구를 구현하는 방법으로 제안된 내용이며, 세부 규격으로 확정하지 않았다.

- 공통 진입 절차에서 역할·작업대·기억을 준비하고, 실행 옵션별 연결부가 인자·지침·훅에 맞춰 전달한다.
- 관계 엔진에서 기억 ID, 근거, 적용 역할·조건, 검토 상태, 보완·충돌·대체 관계를 관리한다.
- 의미가 비슷한 기억은 중복 후보로 제시하여 신규·병합·보완·대체 여부를 검토한다. 의미 중복의 완전 자동 판정을 전제하지 않는다.
- 세션별로 전달한 기억의 항목과 버전, 전달 결과를 기록해 주입 여부를 확인한다.
- 관계 엔진의 항목에서 역할별 경험 view를 생성한다. 생성된 MD의 수정 사항을 원본에 반영하는 방식은 별도 설계한다.

## 아직 결정하지 않은 사항

- jevlike의 재사용 범위, 연결 API, 저장 형식 및 관계 스키마.
- Git 사용 여부와 관리 대상, 로컬 DB 여부, 백업·동기화 방법. 앞서 제안한 MD + Git + SQLite 조합은 채택 결정이 아니다.
- 리뷰 담당자, 검토된 경험으로 인정할 기준, 오래된 기억의 폐기·대체 정책.
- 실행 옵션별 제품·버전과 인증 지원 범위, 첫 모델 호출 전 주입·실패 처리의 실제 보장.
- 사용자가 외부 앱에서 직접 시작했을 때 필요한 협조·설정과 통제 한계.
- 여러 에이전트가 동시에 기억을 고칠 때의 충돌 처리와 권한.
- UI 제품 선택과 일정 관리 기능의 범위.

## 확인할 결과의 예

다음은 수용 기준을 구체화하기 위한 후보이며 실험을 통과한 결과가 아니다.

1. 새 세션이 역할·작업대·현재 업무를 인수하고 지정 위치에서 시작한다.
2. 선택된 기억이 첫 업무 전에 모델 입력에 포함된 근거를 남긴다.
3. 준비 실패를 일으켰을 때 각 실행 옵션이 무엇을 멈추고 무엇을 계속하는지 확인한다.
4. 같은 교훈이 여러 역할 view에 쓰여도 원본 수정이 일관되게 반영된다.
5. 충돌하거나 대체된 기억이 현재 기억과 구분되어 전달된다.
6. 유사한 다음 업무에서 같은 정정이나 완료된 조사가 반복되는지 관찰한다.

## 현재 단계

요구사항 정리와 실행 접점 조사 단계다. 관계 엔진 연결, 옵션별 시작 제어, 경험 view 자동 생성은 아직 구현하지 않았다. 기존 조사와 메모는 근거 자료로 보존하며, 현재 요구의 기준 문서는 이 파일로 둔다.
