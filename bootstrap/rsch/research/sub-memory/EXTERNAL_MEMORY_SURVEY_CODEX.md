# 기억 선별과 변경 반영의 외부 구현 및 연구 비교

작성: Codex, 2026-10-14 KST. 대상: 부모 연구에서 자식 업무에 필요한 기억을 고르고, 근거를 추적하며, 원자료 변경을 의존 결과에 반영하는 기능.

18개 구현·연구·평가·표준 묶음을 비교했다. 외부 사례는 기억을 압축해 전달하는 방식, 관계를 활용해 찾는 방식, 변경된 근거로 파생물을 다시 만드는 방식을 각각 구체화한다. 우리 구현은 **원문과 개정 기록, 업무별 선별, 파생 결과 갱신**을 연결하고 각 단계의 효과를 따로 평가하는 방향이 적합하다. 이는 아래 자료를 우리 요구에 적용한 판단이다.

검색 품질을 높이는 의미 관계와 변경 영향을 계산하는 의존 관계는 구분해야 한다. 같은 저장소에 둘 수 있지만, 비슷한 내용이라는 연결을 재계산 의존성이나 변경 권한으로 사용해서는 안 된다. Byul의 조건부 관계 합성과 목적별 view를 이 경계의 기준으로 유지한다.

## 코드에서 확인한 삭제와 갱신의 차이

다음 세 저장소는 main을 한 번씩 고정한 뒤 같은 커밋의 파일을 읽었다. 원격 코드의 실행 검증은 하지 않았다.

**Graphiti의 삭제는 별도 검증이 필요하다.** `remove_episode`는 episode의 관계를 조회한 뒤 관계의 첫 episode ID가 삭제 대상과 같으면 삭제 대상으로 넣는다. 엔티티는 해당 episode에서만 언급됐을 때 삭제한다. 확인한 함수에는 공유 엔티티 요약을 남은 원문에서 재생성하는 호출이 보이지 않는다. 따라서 이 함수만으로 여러 출처가 합쳐진 요약과 모든 파생 view에서 삭제의 영향을 제거한다고 결론 내릴 수 없다. [graphiti.py L2164](https://github.com/getzep/graphiti/blob/8d8a12a22452cbef9335792afb73b8cbfe6a79fa/graphiti_core/graphiti.py#L2164)

`EntityEdge`에는 episode 목록과 사실 유효 시점, 무효화 시점 필드가 있다. 이는 시간과 출처를 담는 직접적인 구현 근거다. 이 필드의 존재와 전체 삭제 처리의 완전성은 따로 평가한다. [edges.py L263](https://github.com/getzep/graphiti/blob/8d8a12a22452cbef9335792afb73b8cbfe6a79fa/graphiti_core/edges.py#L263)

**LightRAG는 남은 근거를 기준으로 삭제와 재구성을 나눈다.** `_purge_kg_contributions`는 문서의 chunk가 기여한 엔티티·관계를 찾고 남은 출처가 없으면 삭제하며, 있으면 남은 chunk로 재구성한다. 재구성 결과를 저장한 뒤 원문 chunk와 복구용 색인을 제거하도록 순서를 두고 실패 단계도 기록한다. 우리 기억에 출처 A와 B가 있을 때 A만 사라진 경우를 시험할 구체적인 참고 구현이다. [분류와 순서 L6027](https://github.com/HKUDS/LightRAG/blob/4d0afc1bc36e6a34d4a5895b68efe9413748627a/lightrag/lightrag.py#L6027), [남은 출처 L6427](https://github.com/HKUDS/LightRAG/blob/4d0afc1bc36e6a34d4a5895b68efe9413748627a/lightrag/lightrag.py#L6427), [재구성과 저장 L6687](https://github.com/HKUDS/LightRAG/blob/4d0afc1bc36e6a34d4a5895b68efe9413748627a/lightrag/lightrag.py#L6687)

삭제 진입점에는 처리 상태·잠금·재시도 경로가 있다. 다만 best_effort와 rollback 정책, 캐시된 추출 자료의 이용, 여러 저장소에 걸친 실패 조건이 있으므로 원자성이나 원문 영향의 완전 제거를 이번 코드 읽기로 보장하지 않는다. [삭제 진입점 L6727](https://github.com/HKUDS/LightRAG/blob/4d0afc1bc36e6a34d4a5895b68efe9413748627a/lightrag/lightrag.py#L6727)

**LlamaIndex의 전체 동기화와 부분 입력은 다르다.** `_handle_upserts`는 같은 문서 ID의 해시가 바뀌면 기존 문서·벡터 자료를 지우고 변환 대상으로 돌린다. `UPSERTS_AND_DELETE`는 저장된 ID 중 이번 입력에 없는 ID도 삭제 대상으로 계산한다. 이 경로를 부모 자료 일부만 받은 상황에 그대로 적용하면 누락된 입력을 삭제로 오해할 수 있으므로, 수신 범위가 전체인지 증분인지 명시해야 한다는 설계 판단이다. [pipeline.py L469](https://github.com/run-llama/llama_index/blob/5b7b6e323e1da3edd787a2104a89257c14f026d0/llama-index-core/llama_index/core/ingestion/pipeline.py#L469)

변환 캐시의 해시는 입력 내용과 변환 설정을 함께 사용한다. 우리 쪽에서는 요약 프롬프트·추출기·선정 규칙이 바뀐 경우에도 기존 결과를 다시 검토하는 조건으로 확장할 수 있다. [변환 해시 L58](https://github.com/run-llama/llama_index/blob/5b7b6e323e1da3edd787a2104a89257c14f026d0/llama-index-core/llama_index/core/ingestion/pipeline.py#L58)

## 효과 수치를 해석하는 기준

Mem0 논문 Table 2의 같은 실험에서 그래프 추가의 이득과 비용을 함께 볼 수 있다.

| 방법 | 전체 LLM 판정 점수 | 전달 기억 토큰 | 전체 응답 지연 p95 |
| --- | ---: | ---: | ---: |
| Mem0 | 66.88 | 1,764 | 1.440초 |
| 그래프를 추가한 Mem0 | 68.44 | 3,616 | 2.590초 |
| 전체 대화 전달 | 72.90 | 26,031 | 17.117초 |

그래프 추가의 점수 차이는 1.56점이다. Table 1에서는 시간 질문 점수가 오르지만 단일·다단계 질문 점수는 낮아진다. 전체 대화는 더 높은 점수와 더 큰 비용을 보였다. GPT-4o-mini 기반의 저자 실험이며 답할 수 없는 질문 범주는 제외됐다. 현재 제품 순위나 우리 업무의 기대 개선율로 옮길 수 없다. [Mem0 실험 설정과 Tables 1–2](https://arxiv.org/html/2504.19413v1)

GraphRAG의 전역 요약, RAPTOR의 장문 QA, HippoRAG 2의 연관 검색, A-Mem·Hindsight의 대화 기억은 서로 다른 문제와 모델·평가 조건을 사용한다. 각 연구가 보여 주는 구조적 아이디어는 비교할 수 있지만 성능 수치를 한 줄의 제품 순위로 합칠 수는 없다. 그래프 사용 여부만 바꾸려면 나머지 후보 검색·원문 보존·모델·전달 예산을 맞춰야 한다.

앞선 우리 실험의 약 71% 전달량 감소도 수동 선정한 12개 발췌에 대한 바이트 측정이다. 외부 논문의 토큰·QA 점수·지연과 합산하지 않는다. 전체 전달, 선별의 효과, 그래프 추가 효과, 변경 처리 효과를 따로 확인한다.

Jevlike는 위 M02·M03의 후보 판정기를 비교하는 위치에 둔다. 외부 구현의 LLM 판정이나 관계 탐색 성과가 Jevlike의 적합성을 증명하지는 않는다. 공개 구현 후보의 동일성, 한국어 조건 보존, 수동 기준과 독립된 판정 평가는 계속 남아 있다.

## 다음 비교 실험의 구성

비교군은 전체 원문 전달, 검색·태그 기반 선별, 같은 검색에 관계 탐색을 추가한 선별로 둔다. Jevlike를 준비하면 마지막 단계에 후보 판정을 추가한 변형을 비교한다. 선별 비교군은 같은 원문·생성 모델·전달 예산·출처 및 버전 검사를 사용한다. 전체 원문 전달은 별도의 비용 기준선으로 둔다.

관계 그래프의 효과는 관계 탐색을 추가한 비교군과 추가하지 않은 비교군의 차이로 판단한다. 의존성 검사를 그래프 쪽에만 넣고 최신성 차이를 의미 검색의 우위라고 해석하지 않는다.

시험에는 다음 12개 상황을 포함한다.

1. 직접 필요한 기억과 단순히 언급만 된 자료가 함께 있는 경우.
2. 두세 단계를 연결해야 원문 근거가 드러나는 경우.
3. 선정 관계가 빠졌지만 원문 검색으로는 찾을 수 있는 경우.
4. 최신 정정과 이전 지시가 함께 있으며 적용 시점이 다른 경우.
5. 현재 사실과 과거 사실을 각각 묻는 경우.
6. 두 출처 중 하나만 철회되어 남은 근거로 다시 계산해야 하는 경우.
7. 유일한 필수 근거가 삭제되어 전달을 보류해야 하는 경우.
8. 부모가 일부 문서만 새로 보내고 나머지는 그대로 유지하는 경우.
9. 기억 본문은 같지만 새 자료·선정 그룹·추출 설정이 바뀐 경우.
10. 요약에서 역할·예외 조건이 빠져 상세 원문으로 돌아가야 하는 경우.
11. 무효화 알림 유실, 재계산 실패, 계산 중 재수정이 발생하는 경우.
12. 근거가 없거나 충돌이 풀리지 않아 답·전달을 보류해야 하는 경우.

각 결과에는 선택한 기억, 실제 출처, 사용한 개정, 누락·과잉, 최종 업무 행동을 남긴다. 변경 시험에서는 부분 재계산 결과를 같은 최신 입력에서 새로 만든 결과와 비교한다. 결정적 목록·메타데이터는 직접 대조하고, LLM 요약은 문장 일치 대신 필수 주장·조건·근거 보존을 별도 검토한다. 평가는 관계를 작성한 사람이 정한 기대값만으로 끝내지 않는다.

현재 우선 참조할 구현은 Graphiti의 시간·출처 모델, LightRAG의 다중 근거 재구성, LlamaIndex·Skyframe의 변경 관리다. 역할별 전달 단위에는 Letta·LangMem·OpenViking을, 검색 개선 비교에는 HippoRAG 2·A-Mem을 연결한다. 특정 패키지나 저장소 채택은 이 비교 이후에 판단한다.
