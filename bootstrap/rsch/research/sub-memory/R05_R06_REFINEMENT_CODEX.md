# R05 R06 기억 요구사항 정교화 초안

작성: Codex, 2026-10-14 KST. 상태: 기초 조사·사례 검토·선별 및 갱신 프로토타입 실험을 반영한 요구사항 제안.

목적은 경험을 다음 업무에 재사용하면서 잘못된 병합·충돌 판정·오래된 기억 전달을 줄이는 것이다. [요구사항 원본](../../requirements/REQUIREMENTS_CODEX.md)의 R05·R06을 기준으로, 프로그램의 확인 시점과 실패 처리를 구체화한다. 아래 제안은 부모 요구사항을 대체하지 않는다.

## 확인한 요구와 연구 범위

- 작업 기록·사용자 정정·성공과 실패를 보존하고, 일회성 상태와 재사용할 교훈을 구분한다.
- MD 내부와 문서 사이의 의미 중복·충돌·관계 누락을 다룬다. 역할별 MD는 관리되는 기억에서 생성하는 view로 만든다.
- 사용자의 추가 지시인 “Jevlike도 연구사항에 포함됩니다”를 적용한다. jevlike의 식별, 실제 구현, 관계 판정에 대한 적합성도 조사한다. 구현 경로 제공을 연구 시작의 선행조건으로 두지 않는다.
- 도메인이 필요한 기억을 선택한다. OAuth 인증 모델 직접 연결 / Codex CLI / Claude Code CLI에 전달하는 실제 실행 접점은 부모 rsch의 조사와 연결한다.
- Git·SQLite·전용 그래프 DB와 세부 검토 정책은 미선정이다.

## jevlike에서 확인한 입력과 출력

공개 구현 후보는 [vinnylarouge/jevlike](https://github.com/vinnylarouge/jevlike/tree/94f5fd1b0b11d52bbdfdf4e0ee6aa96b568f8452)다. main을 `94f5fd1b0b11d52bbdfdf4e0ee6aa96b568f8452`로 고정하여 README와 핵심 텍스트 코드를 읽었다. 사용자가 염두에 둔 구현과의 동일성은 아직 미확인이다. aaaNew 아래 MD·JSON·TOML 문서 검색에서는 기존 요구·기억 기록만 확인했다. 이는 로컬 구현 전체가 없다는 판정은 아니다.

이 모델은 문맥과 미리 주어진 선택지 목록을 받아 선택지별 확률을 출력한다. 학습 데이터에는 정답 선택지의 인덱스가 필요하다. README는 독립적인 연구용 출발점으로 설명한다. [고정 README](https://github.com/vinnylarouge/jevlike/blob/94f5fd1b0b11d52bbdfdf4e0ee6aa96b568f8452/README.md)

예측 경로는 모델의 점수에 softmax를 적용해 선택지별 값을 출력한다. 이 경로에 검토 승인이나 기억 원본 변경은 포함되어 있지 않다. 따라서 기억의 관계 후보를 평가하는 부분에 적용할 가능성을 검토하되, 확정 관계의 저장과 변경 책임은 별도로 요구해야 한다. 이는 코드에서 도출한 설계 제안이다. [predict.py](https://github.com/vinnylarouge/jevlike/blob/94f5fd1b0b11d52bbdfdf4e0ee6aa96b568f8452/jevlike/predict.py), [model.py](https://github.com/vinnylarouge/jevlike/blob/94f5fd1b0b11d52bbdfdf4e0ee6aa96b568f8452/jevlike/model.py)

기본 byte 인코더의 README상 한도는 문맥 192바이트, 선택지 32바이트다. 실제 전처리도 UTF-8 바이트를 설정된 길이에서 자른다. 긴 한국어 기억의 적용 조건이 잘릴 수 있으므로 입력 보존 여부를 검증해야 한다. [README](https://github.com/vinnylarouge/jevlike/blob/94f5fd1b0b11d52bbdfdf4e0ee6aa96b568f8452/README.md), [data.py](https://github.com/vinnylarouge/jevlike/blob/94f5fd1b0b11d52bbdfdf4e0ee6aa96b568f8452/jevlike/data.py)

평가 코드는 top-1·top-3·보정 오차와 문맥을 바꾼 대조군을 산출한다. 기억 관계 판정에 대한 성능은 별도 데이터로 확인해야 한다. 이번 결과는 문서·소스 확인이며 모델 실측은 아니다. [eval.py](https://github.com/vinnylarouge/jevlike/blob/94f5fd1b0b11d52bbdfdf4e0ee6aa96b568f8452/jevlike/eval.py)

## Byul 선행연구와 그래프 연구 범위

사용자 지시로 그래프 도입을 연구 범위에 포함하고 Byul 기존 연구를 먼저 확인했다. [Byul 선행연구 검토](BYUL_GRAPH_RESEARCH_CODEX.md)에 기준 커밋·근거 문서·구현 범위와 적용 제안을 남겼다.

- 목적별 공통 view·역할별 view와 필요 시 원자료 재조회라는 선행 구상을 기억 선택에 연결한다.
- 출처·적용 범위·충돌·대체·계산 의존 관계를 구분하고, 연결 경로가 있다는 사실만으로 전달이나 대체를 확정하지 않는다.
- 원자료 변경 시 영향을 받는 view를 찾아 갱신한다. view가 보존할 조건과 생략할 내용을 명시한다.
- Byul v0.1의 고정 문서 목록 기반 view·라우팅·가상 변경 추적은 실험 코드다. 일반 기억 그래프나 실행 차단이 완성된 것으로 취급하지 않는다.

[선별·근거 추적·변경 반영 구현 연구](GRAPH_IMPLEMENTATION_STUDY_CODEX.md)에서 12개 발췌 항목·5개 업무를 전체 전달, 같은 기준의 목록, 관계 그래프, SQLite 관계 조회로 비교했다. 선별 전달량은 공통 직렬화 기준 약 71.4% 줄었지만 목록과 그래프의 결과는 같았다. 수동 지정 관계를 사용했으므로 의미 판정 성능 증거는 아니다.

변경 영향은 한 사례에서 6개 view 중 2개였으며 목록의 의존 검사도 같은 대상을 찾았다. 최종 프로토타입의 19개 확인 항목은 통과했다. 오래된 발췌문에 새 원본 버전만 붙이는 재생성은 보류하고, 가상으로 바꾼 원문을 재추출한 뒤에만 준비 상태가 됐다. 관계 누락·오분류는 그래프만으로 검출하지 못했다.

M05에는 실제 사용한 원문 개정과 기억 내용의 일치, 선정 규칙·그룹 구성 버전, 사용 직전 검사, 재생성 실패 시 보류를 구체화한다. 이는 도입 제안이며 실제 실행기 차단은 미검증이다. 전용 그래프 DB와 최종 저장소는 미선정이다.

## 외부 구현과 연구의 추가 비교

사용자 요청에 따라 18개 구현·연구·평가·표준 묶음을 [외부 사례 비교](EXTERNAL_MEMORY_SURVEY_CODEX.md)에 정리했다. Graphiti·LightRAG·LlamaIndex는 커밋을 고정해 관련 코드도 확인했다. 제품 채택이나 외부 벤치마크 재현은 하지 않았다.

- M01·M02: 사실·요약·추론을 구분하고 의미 관련성, 근거 관계, 계산 의존 관계를 별도로 표현한다. 출처 집합과 사실 시점·수신 시점을 기록한다.
- M03: 그래프 후보가 부족할 때 원문 검색으로 돌아가고, 전달 예산 때문에 역할·예외 조건이 잘리는지 확인한다. Jevlike는 이 후보 판정 단계의 비교 대상이다.
- M04·M05: 전체 동기화와 일부 자료 수신을 구분한다. 출처 하나가 삭제되면 남은 근거로 다시 계산하고, 선정 그룹·규칙·추출 설정 변경도 재계산 조건에 포함한다.
- M06: 같은 모델·선별 예산·출처 및 버전 검사 아래 목록/검색과 그래프 추가를 비교한다. 최신성·누락·과잉·보류·유지 비용·재작업을 별도 지표로 둔다.

외부 근거에서 그래프 추가의 정확도 상승이 모든 질문 유형에 공통되지 않고 지연·전달량도 늘어날 수 있음을 확인했다. 상세 수치는 원 논문의 설정과 함께 외부 사례 비교에 남겼다. 다음 시험에는 다중 출처 중 일부 삭제, 부분 자료 수신, 선정 규칙만 변경 등 12개 상황을 포함한다.

## Jevlike 계열의 판단 효용

사용자의 “기억의 판단과 구별에 jevlike들이 얼마나 쓸모가 있을지”에 따라 [판단 효용 비교](JEVLIKE_MEMORY_UTILITY_CODEX.md)를 추가했다. 원 Jev, 학습 출발점인 vinnylarouge/jevlike, 학습된 Kev, 후보 문자열 점수화 중심의 open-jev, 게임 중심 NanoJev와 NLI 기준선을 구분했다.

기대 역할은 반복되는 의미 중복·보완·충돌 후보의 분류와 검토 순위 조정이다. 구조화된 역할·날짜·버전 비교는 코드가 담당하고, 대체·삭제·검증 완료 승격은 별도 변경 정책과 근거로 판단한다. 부분 중복과 보완은 동시에 성립할 수 있으므로 적용 범위·공통 주장·양립 가능성·정보 부족을 나눠 묻는 방식을 제안한다.

M02에는 다중 관계와 방향, M03에는 입력 보존과 후보 누락·선택지 순서·한국어 평가, M04에는 판정과 변경의 분리, M06에는 허용한 오류 수준에서의 처리 비율과 실제 호출·검토·재작업 감소를 보완한다. 기본 Jevlike 입력 절단 문제는 여전히 해결 전이며 모델 성능은 측정하지 않았다. 사전학습된 판단 모델·NLI·일반 LLM을 같은 사례로 비교한 뒤 자체 학습의 필요성을 판단한다.

## 공개 사례에서 가져온 요구 관점

W3C PROV-DM은 결과물, 그것을 만든 활동, 책임 주체와 원본에서의 파생·개정을 연결한다. 여기에서 가져올 요구는 경험 문장뿐 아니라 그 문장을 만든 근거와 검토 결정을 추적하는 것이다. 해당 표준의 스키마 전체를 채택한다는 의미는 아니다. [PROV-DM](https://www.w3.org/TR/prov-dm/)

Graphiti의 공식 설명은 관계에서 원자료로 거슬러 가는 연결과 사실의 유효기간, 이전 사실의 무효화를 제시한다. 여기에서 가져올 요구는 기록된 시점과 적용되는 시점·조건을 구분하는 것이다. 기억의 진실성이나 승인 권한을 이 기능만으로 판단할 수 있다는 근거는 아니다. [Graphiti 공식 README](https://github.com/getzep/graphiti#why-graphiti) — 2026-10-14 열람, 문서 수준 확인.

아래 보류 동작은 설계 후보다. 실제 차단 범위와 예외 정책은 아직 결정하지 않았다.

| M05 역할별 경험 view — R05·R06 | view 생성부가 도메인이 선택한 기억 ID·버전·조건·검토 상태와 생성 기준을 기록한다. 전달 준비 시 원본 변경 여부를 재확인한다. | 충돌 미해결·대체·만료 항목은 현재 유효한 경험과 구분한다. 재생성 실패나 원본 버전 변경을 숨긴 채 현재 view로 표시하지 않는다. 같은 원본을 쓰는 두 역할 view의 갱신과 과거 전달 내역을 확인할 수 있어야 한다. |
| M06 경험의 효과 — R05 | 다음 유사 업무에서 사용한 경험과 다시 발생한 사용자 정정·탐색·재작업을 연결한다. | 파일 생성량을 성공으로 삼지 않는다. 같은 실패가 반복되면 경험 내용·선택·전달·실제 행동 중 어느 단계가 어긋났는지 근거를 남긴다. |

## 사례에서 구체화한 판정 기준
