# 기억 선별·근거 추적·변경 반영 구현 연구

작성: Codex, 2026-10-14 KST. 상태: 선행자료·공식 문서 조사와 작은 오프라인 구현 실험 완료. 제품 채택·실행기 통합은 미정.

사용자 지시: “자 딱 이 영역까지 과연 어떻게 구현할지 구현 효과가 있는지 리서치해봅시다”. 범위는 **부모 자료에서 필요한 기억 선택 → 선정 근거와 출처 추적 → 원자료 변경 시 의존하는 자식 기억 갱신**이다. 그래프와 jevlike는 이 범위에서 평가한다.

이번 결과는 명시적인 관계와 버전 검사를 구현할 수 있다는 근거다. 자료를 선별하면 전달량을 줄일 수 있지만, 같은 선정 기준을 가진 목록보다 그래프가 더 정확하다는 근거는 나오지 않았다. 그래프는 여러 단계의 선정 경로와 갱신 의존성을 함께 관리하는 표현으로 유용하다. 그 편익이 관계 작성·유지 비용보다 큰지는 실제 업무에서 더 확인해야 한다.

## 근거와 구현 범위

[Byul 선행연구 검토](BYUL_GRAPH_RESEARCH_CODEX.md)의 목적별 view, 원자료 재조회, 조건부 관계 합성, 파생 결과 재계산을 출발점으로 삼았다. Byul 기준 로컬 HEAD는 `79c00bfeaa6903a01160378c3603135119937d7e`다. Byul v0.1은 고정 문서 목록·라우팅·가상 변경 추적을 제공하며, 이번 프로토타입은 별도 연구 작업대에서 작성했다.

추가로 확인한 공식 자료의 적용 범위는 다음과 같다. 2026-10-14 열람.

- SQLite는 관계 테이블과 재귀 CTE로 그래프를 탐색할 수 있다. 중복 노드를 제거하는 UNION을 사용한 순환 그래프 조회도 공식 예제에 있다. 이 기능을 이번 작은 관계 조회에 적용했다. 전용 그래프 DB 채택이 이 범위의 선행조건은 아니라는 구현상 판단이다. [SQLite WITH](https://www.sqlite.org/lang_with.html)
- SQLite 읽기 트랜잭션은 일관된 과거 스냅샷을 보며, 동시 쓰기는 하나다. 따라서 DB 안의 일관성과 외부 원문 파일의 최신성은 별도로 확인해야 한다는 설계 결론을 내렸다. 이번 실험은 동시 쓰기·파일 동기화를 검증하지 않았다. [SQLite Transactions](https://www.sqlite.org/lang_transaction.html)
- Microsoft GraphRAG Local Search는 그래프에서 찾은 후보와 연결된 원문을 함께 사용하고, 순위·필터를 적용해 문맥 한도에 맞춘다. 이번 연구에는 후보와 원문 연결을 유지한다는 관점만 참고했다. GraphRAG 설치나 효과 재현은 하지 않았다. [GraphRAG Local Search](https://microsoft.github.io/graphrag/query/local_search/)

## 작은 비교 실험

부모 요구사항·작업 기억·교훈 후보와 Byul 자료 총 7개 파일에서 12개 발췌 항목을 만들었다. 각 항목에는 원본 경로, 행 범위, 파일 SHA-256, 발췌문 SHA-256을 기록했다. 5개 업무의 필요 항목을 연구자가 수동 지정했다. 이는 독립 평가자가 만든 정답이나 의미 검색 성능 평가가 아니다.

5개 업무는 기억 연구 시작, 그래프 설계, 변경 반영, 실행기 인계, UI 범위다. UI·설치 자료는 선별이 가능한지 확인하는 대조 항목이며 이번 구현 범위를 UI·실행기 개발로 넓힌 것이 아니다. 준비된 view는 업무별 5개와 두 업무 결과를 합친 상위 요약 1개로 총 6개다. 그래프에는 노드 32개와 관계 40개가 있다.

| 방법 | 5회 조회의 전달 항목 합계 | 수동 지정 필요 항목 누락 | 불필요한 포함 | 공통 직렬화 기준 UTF-8 바이트 합계 |
| --- | ---: | ---: | ---: | ---: |
| 12개 항목을 매번 전부 전달 | 60 | 0 | 42 | 31,470 |
| 업무별 목록 조회 | 18 | 0 | 0 | 9,011 |
| 종류를 구분한 관계 그래프 탐색 | 18 | 0 | 0 | 9,011 |
| SQLite 재귀 CTE로 같은 그래프 탐색 | 18 | 0 | 0 | 9,011 |

전체 전달 대비 항목 수는 70%, 직렬화 바이트는 약 71.4% 줄었다. 비교한 전달 데이터는 본문·출처 경로·행·원문 해시이며 선택 경로 설명과 운영용 manifest 전체는 제외했다. 이는 토큰 수·모델 요금·응답 시간 절감률이 아니다. 또한 전체 부모 연구를 실험한 것이 아니라 12개 발췌 항목을 기준으로 한 수치다.

목록은 그래프와 같은 관계 스냅샷에서 업무별 항목을 미리 펼쳐 구성했다. 같은 정보로 같은 결과가 나오는 것이 기대 동작이다. 이 비교로 그래프가 관계를 더 잘 발견하거나 기억의 의미를 더 잘 판단한다고 주장할 수 없다.

따뜻한 인메모리 상태에서 5개 조회를 200회 반복한 선택 함수 중앙값은 목록 약 2.54μs, Python 그래프 약 4.98μs, SQLite 그래프 약 19.78μs/조회였다. 구축·자료 읽기·출처 설명·모델 호출·동시 실행 비용을 제외했고 목록은 미리 계산되어 있다. 작은 한 번의 실행 측정이므로 운영 성능 순위나 확장성 근거로 쓰지 않는다.

## 변경과 실패에서 관찰한 결과

19개 구현 확인 항목이 통과했다. 프로그램이 미리 정한 구조와 버전 조건을 지키는지 확인한 결과이며 의미 정확도 100%라는 뜻은 아니다.

- **변경 범위:** Byul 공통 view 자료 하나의 변경 영향은 그래프 설계 view와 그것을 사용하는 상위 요약, 2개였다. 총 6개 중 나머지 4개는 이 의존 경로의 영향 대상이 아니었다. 관계를 역방향으로 따라 노드 6개·연결 5개를 방문했다. 모든 view의 의존 목록을 검사하는 방법도 같은 2개를 찾았다. 실제 재생성 비용 절감률을 측정한 것은 아니다.
- **갱신 알림 유실:** 원본 버전은 바뀌었으나 view의 무효화 알림을 생략한 상황에서도, 사용 직전 의존 버전을 비교하는 함수가 오래된 묶음을 보류했다. 원본 변경을 시스템이 아예 관찰하지 못한 상황은 이 검사가 해결하지 못한다.
- **버전만 바꾼 재생성:** 첫 구현에서는 기존 발췌문을 새 원본 버전과 연결할 수 있는 허점이 있었다. 최종 구현은 발췌문이 참조하는 원본 해시, 발췌문 내용 해시, 기억 노드 버전이 일치하는지 확인한다. 오래된 문장을 새 버전으로 표시하는 재생성은 보류됐다.
- **가상 원문 재추출:** 원본 파일을 수정하지 않고 메모리 속 복사본에 `VIRTUAL STUDY CHANGE ONLY` 표시를 추가했다. 바뀐 복사본에서 다시 추출하고 기억 버전까지 갱신한 뒤에야 준비 상태가 됐다. 이는 재추출·버전 일치 시험이며 새 의미를 이해하거나 요약하는 능력의 검증은 아니다.
- **삭제:** 사용 중인 필수 원자료를 비활성화하면 기존 묶음 사용과 새 묶음 생성을 모두 보류했다. 남은 근거만으로 충분한지 판정하여 다시 구성하는 삭제 정책은 아직 구현하지 않았다.
- **새 관계:** 선정 그룹에 항목을 추가하면서 그룹 버전을 갱신하면 이전 선정 결과는 보류되고 재조회에는 새 항목이 포함됐다. 선택된 문장 버전만 추적해서는 새 항목의 유입을 알 수 없으므로 그룹·선정 규칙의 버전도 필요하다.
- **잘못된 경로:** 단순 언급인 MENTIONS 관계는 기억 선택에 쓰지 않았다. 알 수 없는 업무는 보류했고, Python·SQLite 조회 모두 시험한 순환에서 중복 없이 종료했다.

의도적으로 잘못된 관계를 넣은 두 사례는 그래프의 한계를 보여 줬다. 필요한 연결 하나를 누락하자 그래프 설계 업무의 필요 항목 6개 중 1개가 빠졌고, 최신성 검사는 READY를 반환했다. 반대로 설치 정보를 선정 관계로 잘못 연결하자 불필요한 자료가 포함됐다. **최신성과 의미적 충분성은 다른 조건이다. 관계가 잘못되면 올바른 탐색도 잘못된 결과를 전달한다.**

파일 전체 해시의 단점도 확인했다. 부모 README의 설치 표만 바뀌어도 파일 버전을 기준으로는 그 안의 다른 발췌문을 쓰는 5개 view가 영향 대상이 된다. 초기에는 이런 보수적 재검사가 단순하고, 실제 비용이 커지면 문단·기억 단위 변경 추적으로 세분화할 수 있다. 문단 이동과 적용 조건 변경을 놓치지 않는 방식은 추가 연구가 필요하다.

## 구현할 최소 데이터

다음은 제품 설계 제안이며 프로토타입이 모든 필드를 구현했다는 뜻은 아니다.

| 데이터 | 최소 역할 | 필요한 정보 |
| --- | --- | --- |
| 원자료 개정 | 무엇을 읽었는지 고정 | 원자료 ID, 개정 ID/내용 해시, 위치, 수신 시점, 활성·삭제 상태 |
| 기억 개정 | 재사용할 주장과 조건 | 기억 ID, 본문·버전, 역할·업무·시점 조건, 원자료 개정과 구간, 확인 수준 |
| 관계 | 선택 이유와 의존성 표현 | 양쪽 ID, 관계 종류, 적용 조건, 근거·검토 상태, 관계/그룹 버전 |
| 선정 기준 | 현재 업무에 필요한 범위 | 업무·역할, 조회 규칙, 규칙·후보집합 버전, 필수 조건, 전달 예산 |
| 전달 묶음과 manifest | 실제 전달물의 추적·재검사 | 포함한 기억 버전, 선정 경로, 원문·관계·규칙 버전, 생성 상태와 보류 이유 |

현재 실험은 정해진 관계를 사용한다. 실제 필요한 관계는 `업무가 선택함`, `그룹에 포함됨`, `원문에서 파생됨`, `view가 의존함`부터 시작할 수 있다. 충돌·대체·유사 관계는 각각 별도 의미를 유지하고, 유사하다는 이유만으로 선택·삭제·대체하지 않는다. 관계를 수정하는 작업과 그 관계를 포함한 그룹 버전 갱신은 함께 완료되어야 한다.

## 통제 주체와 개입 시점

| 시점 | 프로그램의 동작 제안 | 실패 처리와 경계 |
| --- | --- | --- |
| 부모 자료를 수신할 때 | 도메인의 기억 관리부가 원문 개정을 저장하고 발췌·조건·출처를 연결한다. | 관찰한 개정과 실제 읽은 내용이 다르면 다시 읽는다. 출처가 없는 내용은 검토 후보로 구분한다. |
| 자식 업무를 시작할 때 | 도메인이 현재 업무·역할에서 허용된 선정 관계만 따라간다. | 업무 미등록, 필수 조건 부족, 미해결 충돌이면 해당 묶음 전달을 보류하고 부족한 근거를 반환한다. |
| 기억 묶음을 만들 때 | 실제 사용한 원문·기억·선정 규칙·그룹의 버전을 manifest에 기록한다. | 근거의 버전 불일치나 삭제를 무시하고 READY로 만들지 않는다. 내용 보존은 별도 점검한다. |
| 실행기에 전달하기 직전 | 기억 관리부가 최신 등록 버전과 manifest를 대조하고, 전달 연결부가 그 결과를 확인한다. | 불일치하면 해당 묶음을 새로 계산한다. 프로토타입은 serve 함수만 확인했으며 CLI·모델 호출 차단은 아직 구현하지 않았다. |
| 원문이나 관계가 바뀔 때 | 변경을 등록하면서 역방향 의존 경로의 결과를 오래된 상태로 만들고 재계산 대상으로 잡는다. | 재계산 실패 시 이전 묶음을 최신으로 표시하지 않는다. 필수/선택 기억에 따른 부분 진행 정책은 별도 결정한다. |
| 재계산을 완료할 때 | 새 원문에서 기억을 다시 만들고, 선정 규칙을 다시 적용한 뒤 참조 버전을 대조한다. | 처리 도중 또 바뀌었으면 결과 공개를 보류하고 새 개정으로 재시도한다. 버전 표시만 바꿔 완료하지 않는다. |

흐름은 `업무·역할 → 선정 기준 → 필요한 기억 + 원문 연결 → 버전 검사 → 전달`이다. 변경 흐름은 `원문/관계 변경 등록 → 영향받는 묶음 무효화 → 재추출·재선정 → 버전 검사 → 새 묶음 공개`다. 과거 실제 전달 이력과 현재 전달 가능한 상태는 구분한다.

동시 변경에 대해서는 같은 개정 스냅샷에서 계산하고, 공개 직전에 참조 개정을 비교하는 방식이 후보이다. 외부 파일 변경을 수집하지 못하거나 실행기가 검사를 우회해 예전 파일을 읽으면 보장이 깨진다. 실제 통합 단계에서 변경 등록·묶음 공개의 원자성, 실패 재시도, 우회 경로를 검증해야 한다. 이번 프로토타입의 READY/BLOCKED를 그 실행 보장으로 확대하지 않는다.

## jevlike의 자리

jevlike의 공개 구현 후보는 문맥과 주어진 선택지의 점수를 계산한다. 이번 흐름에서는 관계 후보의 분류·평가에 배치할 가능성을 검토할 수 있다. 어떤 기억을 후보로 찾을지, 원본 버전을 어떻게 보존할지, 검토 후 관계를 어떻게 확정할지, 바뀐 view를 언제 다시 만들지는 별도 기능이다. 근거와 동일성의 미확인 사항은 [정교화 초안](R05_R06_REFINEMENT_CODEX.md)에 유지한다.

이번 실험의 관계는 수동 지정했고 jevlike 모델을 실행하지 않았다. 앞선 한국어 입력 333바이트가 기본 한도 192바이트에서 자식 역할 조건을 잃는 사례도 해결된 것으로 취급하지 않는다. 관계 판정 후보는 입력 보존 확인 후, 현재 연구자가 만든 기대값과 독립된 사례로 평가해야 한다.

## 구현 효과에 대한 판단

- **구현 근거가 생긴 부분:** 한정된 관계 조회, 선택 경로 기록, 영향 대상 추적, 준비된 묶음의 버전 검사, 가상 원문 재추출은 작은 코드로 작동했다. SQLite에서도 같은 선별 결과가 나왔다.
- **효과가 관찰된 부분:** 미리 정한 기준으로 선별하면 전달량이 줄고, 등록된 변경과 맞지 않는 준비물은 보류할 수 있다. 영향 범위가 작은 변경에서는 재검사·재생성 대상을 좁힐 수 있다.
- **아직 입증하지 못한 부분:** 그래프가 좋은 관계를 자동 발견하는지, jevlike가 그 판정을 잘하는지, 실제 사용자의 재설명·오류·재작업이 줄어드는지, 관계 유지 비용을 포함해 이득인지, 대규모·동시 실행에서도 안전한지.

현 시점의 제안은 **원문 근거, 종류가 분명한 관계, 버전 manifest를 가진 작은 선별·갱신 계층**부터 검증하는 것이다. 이 자료 규모에서는 목록도 충분한 기준선이다. 전용 그래프 DB와 대규모 GraphRAG 도입을 선택할 근거는 아직 없다. SQLite는 이번 구현 실험의 도구이며 최종 저장소 채택 결정이 아니다.

후속 한 단계는 같은 범위 안에서 부모의 실제 결과 갱신 사례 하나를 재생해, 사전 관계를 만든 사람과 별개로 필요한 기억을 검토하고 누락·과잉·재작업을 관찰하는 것이다. 이를 통해 관계 작성 비용을 포함한 효과를 판단할 수 있다. 실제 실행기 연결은 부모 rsch의 실행 접점 조사와 맞춰야 한다.

## 외부 사례를 반영한 후속 평가

사용자의 추가 요청에 따라 [외부 구현과 연구 비교](EXTERNAL_MEMORY_SURVEY_CODEX.md)를 작성했다. 이 실험의 결과 수치를 변경하지 않고, 검색 후보 누락의 원문 조회 보완, 다중 근거 중 일부 삭제, 일부 자료 수신과 전체 동기화의 구분, 생성 규칙 변경의 의존성 추적을 후속 시험으로 구체화했다. 같은 출처·버전 검사를 목록/검색 기준선에도 적용해 그래프 탐색 자체의 추가 효과를 분리한다.

## 재현 자료와 제한

- 코드: [study.py](graph-pilot-20261014/study.py)
- 입력 발췌·원본 해시·관계·수동 기대값: [dataset.json](graph-pilot-20261014/dataset.json)
- 최종 결과와 19개 확인 항목: [results.json](graph-pilot-20261014/results.json)
- 보완 전 탐색 실행 결과: [results.initial.json](graph-pilot-20261014/results.initial.json). 최종 근거는 results.json이다.

Python 3.12.14, SQLite 3.53.1의 표준 라이브러리만 사용했다. SQLite는 인메모리 DB였다. 실행은 같은 작업대에서 번들 Python에 `-B`와 `graph-pilot-20261014/study.py`의 절대 경로를 전달했다. 스크립트는 실행 시 현행 원본을 읽으므로 이후 원문이 바뀌면 결과도 달라질 수 있다. 저장된 dataset에는 이번 발췌와 해시가 있으며 원본 전체의 불변 스냅샷을 별도로 복제하지 않았다.

발췌는 지정 구절부터 빈 행까지를 사용하며 줄바꿈을 정규화한다. 자동 의미 단위 추출, 주변 목록·조건의 충분성, 원문 전체의 바이트 복원은 검증하지 않았다. 선정 trace는 한 경로를 기록하고 모든 대체 경로의 설명을 보장하지 않는다. 실험 시작·종료의 7개 원본 해시는 같았으며 부모·Byul 원본을 수정하지 않았다. 패키지 설치·모델 호출·Byul 테스트 재실행·제품 변경은 하지 않았다.
