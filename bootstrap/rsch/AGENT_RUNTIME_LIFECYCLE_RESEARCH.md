# Agent Runtime Lifecycle 연구

- 작성일: 2026-10-14
- 상태: 연구 진행 중 / 기존 결과 1차 취합 및 부트스트랩 읽기 순서 초안
- 목적: 에이전트가 시작하고, 작업하고, 중단·복구하고, 결과와 경험을 남기는 전체 수명주기를 기존 연구와 코드 근거로 정리한다.
- 문서 성격: 연구 노트. 기존 설계의 채택, 새 아키텍처의 확정, 구현 완료를 선언하지 않는다.

## 1. 연구 배경과 범위

사용자는 기존 AAA의 분류와 문서 파편화를 검토하면서 4분할 구조 자체도 재검토하겠다고 밝혔다. 이번 연구는 기존 폴더 배치를 정답으로 삼지 않고 런타임의 실제 동작과 책임을 기준으로 취합한다.

이 연구 문서는 aaaNew/bootstrap/rsch에 둔다. 폴더 생성은 구현이나 상세 설계의 확정을 뜻하지 않는다.

연구 범위는 다음과 같다.

1. 부트스트랩: 시작 시 무엇을 누가 로딩하는가.
2. 정체성·역할·작업·권한: 이번 실행의 주체와 범위는 어떻게 정해지는가.
3. 상태 복원: 이전 실행의 결과와 실제 변경을 어떻게 확인하는가.
4. 컨텍스트: 소스와 기억을 어떤 기준으로 선택하고 갱신하는가.
5. 실행: 작업을 나누고 개별 실행 시도를 어떻게 추적하는가.
6. 결과와 검토: 응답, 산출물, 실제 효과, 완료를 어떻게 구분하는가.
7. 중단·재개·취소·복구: 실행 도중 조건이 바뀌면 어떻게 처리하는가.
8. 기억과 학습: 무엇을 남기고, 검증하고, 다음 실행에서 사용하는가.
9. 종료와 인계: 다음 실행이 추측 없이 이어받으려면 무엇을 보존해야 하는가.

## 2. 취합 기준

- 사용자 지시, 기존 연구의 설계, 코드 정적 관측, 실제 실행 증거, 조사자의 제안을 구분한다.
- 문서의 제목이나 완료 표기만으로 제품 채택·운영 성공을 인정하지 않는다.
- 기존 자료는 원본 경로와 고정 commit으로 참조한다. 원문 전체를 새 문서에 복제하지 않는다.
- 이번 문서는 이미 조사한 근거를 우선 취합한다. 모든 과거 연구를 정독·통합한 최종본은 아니다.
- 기존 AAA 저장소와 branch는 변경하지 않는다. 이 문서 작성 과정에서는 런타임 실행이나 테스트를 수행하지 않았다.

## 3. 현재까지 취합한 수명주기

아래 흐름은 기존 연구를 실행 세션 관점에서 종합한 설명이다. AAA 전체 런타임의 실제 동작을 입증한 결과는 아니다.

```text
시작
  → 기본 지침과 실행 설정 로딩
  → 정체성·작업·권한 확인
  → 현재 상태와 이전 효과 복원
  → 필요한 소스·기억 선택
  → 실행 조건 확인 및 개별 시도 수행
  → 결과·실제 효과 확인
  → 검토·수정·완료 판단
  → 다음 작업 / 대기 / 종료

중단·오류·지시 변경 발생
  → 현재 상태와 실제 효과 확인
  → 재개 / 재계획 / 복구 / 보류

검증된 실행 결과와 경험
  → 재사용 후보 검토
  → 허용된 기억 반영
  → 후속 실행에서 사용 및 효과 평가
```

### 3.1 서로 다른 수명

| 대상 | 의미 | 구분해야 하는 점 |
| --- | --- | --- |
| Runtime 세션 | 에이전트가 실행되는 한 구간 | 세션 종료가 사용자 목적 달성을 뜻하지 않는다. |
| Work | 사용자가 달성하려는 목적 | 여러 Task와 여러 세션에 걸칠 수 있다. |
| Task | 목적을 위한 개별 작업 | 해당 작업의 완료 기준을 따로 확인한다. |
| Attempt | 작업을 수행한 개별 시도 | 결과 확보·검증·효과 확인이 필요하다. |
| Persona·Memory | 실행이 사용하는 정체성과 기억 | 세션이나 저장 위치가 바뀌어도 소유권을 새로 만들지 않는다. |

Work·Task·Attempt의 구분과 각각의 완료·종료 조건은 S1·S2의 설계 근거다. Runtime 세션을 위 표처럼 설명한 것은 이번 취합의 관점이며, 기존 연구에 구현된 별도 상태 enum이라고 주장하지 않는다.

### 3.2 결과, 완료, 종료

S1·S2는 생성 → 실행 허용 → 실행 중 → 결과 확보 → 검증 → 완료 인정 → 종료 정리를 구분한다. 대기·차단·실패·취소는 각 원인과 근거를 따로 남긴다.

모델 응답의 종료, Attempt의 성공, Task의 완료, Work의 목적 달성은 각각 확인해야 한다. 하위 작업의 종료가 상위 작업을 자동으로 완료시키지는 않는다.

검토에서 수정이 필요하면 수정된 버전을 대상으로 영향 범위를 재검증한다. 검토 완료와 사용자 수용도 별도로 다룬다.

### 3.3 중단과 복구

S1·S2는 정지 요청과 실제 정지 관측, 취소와 이미 발생한 변경의 되돌리기를 구분한다. 재개할 때 현재 권한·입력 버전·실제 효과를 다시 확인한다.

변경 여부가 불명확하면 기존 실행과 대상을 먼저 조회한다. 응답 유실이나 시간 초과만으로 아무 변경도 없었다고 간주하지 않는다. 이미 확인된 변경은 중복 수행하지 않는다. 이러한 판단의 일부는 S5·S6 코드에서도 정적으로 확인했다.

### 3.4 컨텍스트와 기억

S1은 원본의 정확한 버전과 적용 범위를 확인한 뒤 필요한 자료를 선택하는 ContextPlan을 설계한다. 작업 전환, 중요한 결과, 정보 부족, 검토 지적 등 유효한 변화가 생기면 다시 평가한다.

경험은 즉시 확정된 지식이나 규칙이 되지 않는다. 관측과 해석을 구분하고, 재사용 후보의 검증과 반영 허용을 거친다. 정책·Skill 변경은 별도 권한 경로다.

Current는 현재 작업 상태를 보여주는 요약이라는 설계 의미를 가진다. 정확한 원본과 권한을 대신하는 새 정본으로 취급하지 않는다.

## 4. 부트스트랩에서 무엇을 어떤 순서로 읽는가

### 4.1 확인된 동작과 이번 제안

Codex는 작업 시작 전에 정해진 탐색 범위의 AGENTS.md 등을 초기 지침으로 로딩한다. 로딩한 문서가 가리키는 다른 자료와 기억까지 전부 자동으로 읽는다는 뜻은 아니다. 탐색 범위·override·용량 제한 등의 세부 동작은 S8 공식 문서를 따른다.

현재 대화에 제공된 옛 AAA 로컬 진입 지침은 원격 main을 한 번 고정하고 같은 snapshot의 AGENTS.md → core/AGENTS.md → core/CURRENT.md → core/planning/CURRENT.md를 읽도록 요구한다. 이는 기존 AAA의 경로이며 aaaNew에 그대로 도입하기로 결정한 경로가 아니다.

아래는 S1의 정체성·범위 결속, 컨텍스트 선택, 복구 절차를 바탕으로 정리한 aaaNew 읽기 순서의 연구 초안이다. AAA 런타임에 구현되거나 사용자에게 채택된 순서라고 주장하지 않는다. 각 행은 필요한 정보의 묶음이며, 행마다 파일·폴더·서비스를 만들라는 뜻이 아니다.

### 4.2 기본 읽기 순서

런타임은 먼저 실제 작업 위치, 사용 가능한 도구·권한, 이미 전달된 상위 지침과 현재 사용자 요청을 제공해야 한다. 이 실행 환경 정보까지 저장소 문서의 자기 선언으로 대체하지 않는다.

| 순서 | 읽는 대상 | 확인할 내용 | 읽은 뒤 확보할 것 |
| --- | --- | --- | --- |
| 1 | 짧은 진입 지침. AGENTS.md는 그 후보 | 이 환경의 목적, 공통 행동 기준, 적용 지침의 범위, 다음 자료의 정확한 위치·읽는 조건 | 어디서 시작하며 무엇을 추가로 읽을지 |
| 2 | 현재 요청·작업 지정과 필요한 정체성·권한 정보 | 사용자 목적과 완료 기준, 맡은 역할, 대상 프로젝트·도메인, 소스·기억 접근 범위, 허용된 변경 | 이번 실행의 목적·책임·범위. 폴더 이름만으로 역할이나 권한을 추정하지 않음 |
| 3 | 해당 작업의 현재 상태 | 새 작업인지 재개인지, 완료·미완료·대기 항목, 이전 결과와 실제 변경, 확인되지 않은 효과 | 이미 수행한 일과 남은 일. 새 작업에 이전 상태가 없다면 명시적으로 건너뜀 |
| 4 | 현재 행동에 적용되는 필수 규칙과 원본 근거 | 관련 사용자 결정·요구사항, 작업 범위의 지침, 대상 코드·설계·데이터, 필요한 Skill의 절차 | 현재 판단에 필요한 정확한 원문과 버전 |
| 5 | 해당 작업에 필요한 기억 | 관련 경험·사용자 선호·검증된 지식, 근거와 적용 범위, 현재 소스와의 유효성 | 원문을 보완하는 재사용 정보. 기억이 없으면 필수 정보인지 판단하고 진행 |
| 6 | 실행 직전의 변경 여부 | 목적·권한·작업 상태·선택한 원문과 기억이 읽는 동안 바뀌었는지, 첫 행동과 검증 방법이 명확한지 | 다음 행동을 시작할 수 있는 현재 맥락 |

실행 환경 확인 → 진입 지침 → 작업·정체성·권한 → 현재 상태 → 필수 원문 → 관련 기억 → 실행 직전 확인의 순서다. 이미 초기 컨텍스트에 전달된 정보는 먼저 그 내용을 사용하고, 누락되거나 바뀐 부분을 추가로 읽는다.

이 순서는 의존 관계를 표현한다. 2단계의 기본 접근 범위를 확인한 뒤에도 개별 자료를 읽기 전에는 해당 자료의 소유자·적용 범위·허용 여부를 확인한다. 읽기 허용 여부를 판단하는 데 필요한 규칙은 그 자료보다 먼저 읽는다. 특정 기억을 이해하려면 추가 원문이 필요할 수 있으며, 이때는 4단계로 돌아간다.

읽는 순서와 지시의 우선순위는 다르다. 나중에 읽은 기억·과거 보고서·외부 자료가 현재 사용자 요청이나 적용되는 상위 지침을 덮어쓰는 권한을 갖지는 않는다. 같은 권한 범위의 지시가 충돌하면 출처와 적용 시점을 확인하고, 판단할 수 없는 부분을 임의로 확정하지 않는다.

### 4.3 진입 지침에 담을 최소 정보

진입 지침은 부트스트랩의 시작점을 찾게 하는 짧은 안내로 제안한다. 다음 내용을 담되, 동적으로 바뀌는 본문은 원본을 가리킨다.

- 이 실행 환경이 무엇을 위한 곳인지.
- 항상 적용되는 공통 기준과 실제 권한을 확인하는 방법.
- 현재 작업과 정체성·역할 정보를 어디서 읽는지.
- 현재 상태, 필수 소스, 관련 기억의 위치를 어떻게 찾는지.
- 자료가 없거나 서로 충돌할 때 무엇을 확인해야 하는지.

모든 아키텍처 문서, 과거 연구, 교환 기록, 기억 전체를 진입 지침에 포함하거나 일괄 필독으로 지정하지 않는다. 이미 적용 중인 사용자 지시에서 추가 읽기를 요구한 경우에는 그 범위를 따른다.

AGENTS.md라는 이름과 탐색 동작은 실행 도구에 따라 달라질 수 있다. 도구별 시작 방식에서 같은 기본 지침을 어떻게 전달할지 확인해야 한다. aaaNew의 실제 진입 파일 이름과 데이터 저장 위치는 아직 정하지 않았다.

### 4.4 시작 상황별로 달라지는 읽기

| 상황 | 우선 확인하거나 추가로 읽을 것 | 처리 방향 |
| --- | --- | --- |
| 처음 받은 작업 | 현재 요청, 완료 기준, 적용 규칙과 원본 | 이전 작업 기록이 없어도 작업 정의가 충분하면 시작 |
| 중단 후 재개 | 현재 작업 버전, 현재 권한, 이전 실행 결과·실제 효과, 체크포인트 | 확인된 결과를 이어받고, 불명확한 변경은 재실행 전에 조회 |
| 다른 작업으로 전환 | 새 작업의 목적·역할·범위, 관련 상태·소스·기억 | 이전 작업의 권한과 기억을 새 작업에 자동 적용하지 않음 |
| 지시·소스·권한 변경 | 바뀐 원문과 영향을 받는 기존 상태·기억 | 필요한 부분의 맥락을 다시 구성하고 현재 행동의 허용 여부 재확인 |
| 맡은 작업이 없음 | 진입 지침과 현재 작업 지정 여부 | 임의로 목표나 할 일을 만들지 않고 작업 지정 대기 |

재개 시에는 원래 실행의 식별자로 결과와 효과를 조회한다. 체크포인트의 과거 계획만으로 현재 실행을 허용하지 않는다. 관련 변경이 없는 같은 작업에서는 매 모델 응답마다 전체 부트스트랩을 반복하지 않는다.

### 4.5 읽기 종료와 누락 정보 처리

부트스트랩 읽기의 종료 기준은 다음 질문에 근거를 들어 답할 수 있는지로 제안한다.

1. 이번에 달성할 목적과 완료 기준은 무엇인가.
2. 내가 맡은 역할과 읽기·쓰기 범위는 어디까지인가.
3. 이미 확인된 결과·변경과 아직 확인하지 못한 것은 무엇인가.
4. 다음 판단에 사용할 원본과 기억은 무엇이며 어떤 버전에 근거하는가.
5. 바로 다음 행동은 무엇이고 그 결과를 어떻게 확인할 것인가.

필수 원문·권한·효과 확인이 부족하면 그 정보에 의존하는 행동을 보류하고 필요한 정보만 확인한다. 이미 허용된 행동에 같은 승인을 반복 요청하지 않는다. 관련 기억이나 과거 연구가 없다는 이유만으로 독립적으로 가능한 작업까지 중단하지 않는다. 필요한 지침이 용량을 넘으면 중요 제약을 임의로 누락하지 않고 읽기 범위나 작업 단계를 나눈다.

이 질문들에 답하기 위해 매번 별도의 시작 보고서를 작성하도록 요구하지는 않는다. 실제로 전달·선택된 지침과 자료를 추적할 수 있는 최소 기록의 형식은 구현 연구에서 정한다.

### 4.6 근거와 남은 검증

- S1 §4 C01–C07: 정체성·접근 범위 확인, 정확한 원본 참조, 필수 자료와 용량 관리.
- S1 §8.1–8.3: 범위 확인 후 자료 선택, 모든 조회 경로의 접근 조건 확인, 유효한 변화에 따른 컨텍스트 갱신.
- S1 §14.2–14.4 및 S5·S6: 재개 전 현재 상태·권한·실제 효과 조회, 확인된 변경의 중복 실행 방지.
- S8: Codex의 기본 지침 자동 로딩. 다른 실행 도구의 동작으로 일반화하지 않음.

2026-10-14에 S1의 위 관련 구간을 고정 commit으로 다시 읽어 대조했다. 읽기 순서 자체의 동작 시험은 수행하지 않았다. 후속 검증에서는 새 작업, 중단 후 재개, 오래된 기억과 현재 원문이 충돌하는 경우, 필수 자료가 누락된 경우를 넣고 불필요한 전체 탐색 없이 다음 행동을 정하는지 확인한다.

미확정 사항은 실제 진입 파일, 작업·정체성·상태 정보를 연결하는 방식, 기억의 저장 위치와 조회 방식, 도구별 지침 전달 방식이다.

## 5. 소스·실행 상태·기억의 관계

이 대화에서 조사자는 소스와 실행 중 축적되는 기억을 분리하고, 사용 시에는 하나의 진입점에서 필요한 내용을 조합하는 방안을 제안했다. 사용자 채택은 확인되지 않았으며 연구 선택지로 유지한다.

| 구분 | 다루는 내용 | 검토할 관리 기준 |
| --- | --- | --- |
| 소스 | 코드·원본 문서·명시적 결정의 근거 | 원본 소유자, 정확한 버전, 변경 검토 |
| 실행 상태 | 현재 작업, 실제 변경, 미확인 효과, 복구 단서 | 실행 식별자, 내구성, 재개·중복 방지 |
| 기억 | 경험에서 얻은 지식·선호·재사용할 맥락 | 소유자, 적용 범위, 근거, 유효성·정정 |

논리적 구분과 물리적 저장소 분리는 다른 결정이다. 별도 Git 저장소나 데이터베이스의 종류·개수는 정하지 않았다. 소스가 바뀌면 관련 기억의 유효성을 확인하고, 저장 위치 변경으로 기억의 소유권을 바꾸지 않는 관계를 검토한다.
