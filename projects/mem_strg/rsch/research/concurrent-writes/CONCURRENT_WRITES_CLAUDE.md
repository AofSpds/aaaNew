# S2 동시 쓰기 — 같은 PC에서 세션 여럿이 메모를 쓸 때

- 작성: 2026-10-17, AAA/NEW/RSCH/MEM_STRG · REQ-001 S2
- 실측 환경: HANAL, Windows 11, Python 3.13.14, SQLite 3.50.4, 로컬 디스크(C:, 스크래치 폴더)
- 스크립트: [s2_concurrency_bench.py](s2_concurrency_bench.py) (표준 라이브러리만, 지우는 동작 없음)

> **정정 (2026-10-18, Pro P1·P2 검토 → [REVIEW](../../reviews/STORAGE_ENGINE_OPERATIONS_REVIEW_CLAUDE.md) #1–#3, #11, #12)**
> - kill 시험의 0.03 ms는 강제 종료부터 잠금이 풀리기까지 걸린 시간이 아닙니다. 타이머는 종료를 확인한 뒤에 시작했습니다(§2 본문에도 정정을 적음).
> - "손실 0"은 "이 시험에서 예상한 (w,i) 기록이 빠지지 않음"으로 범위를 줄입니다. 성공한 기록이 장애 뒤에도 남는지(fsync)는 시험하지 않았습니다.
> - "쓰기 CLI 하나"라도 여러 세션이 실행하면 프로세스는 여럿입니다. 잠금은 바이트가 섞이는 것을 막을 뿐입니다. 두 세션이 같은 옛 CURRENT를 바탕으로 쓰면 뒤의 것이 앞의 변경을 덮습니다(논리적 손실). 그래서 §4 규칙에 `expected_revision` 검사를 더해야 합니다.
> - §4-5 "쓰다 만 끝줄은 제외하고 다음 기록은 새 줄에서"는 설계만 있고, 깨진 줄이 파일 중간에 남는 문제의 복구 절차는 없습니다. 후보는 깨진 바이트를 보존하고 새 segment로 이어 쓰는 방식입니다.
> - SQLite 3.50.4는 WAL-reset 버그 범위 안입니다(S1 정정 참고).

## 1. 결론

- **잠금 없이 같은 파일에 쓰면 Windows에서 기록이 사라지고 깨집니다** [실측]. 지금처럼 파일을 고쳐 쓰는 방식은 기록의 36–54%를 잃었습니다.
- **손실이 0인 방식은 세 가지입니다** [실측]: ① 잠금 파일로 순서를 지켜 추가 ② 쓰는 세션마다 자기 파일에 추가 ③ SQLite.
- 권고는 S1의 B안에 이 규칙을 더하는 것입니다 [판단]: **역할별 jsonl 스트림 + 스트림마다 잠금 파일 + 쓰기는 CLI 하나로만.**
- 남은 위험은 기술보다 권한입니다. 저장소가 세션의 작업 폴더 밖에 있으면 Claude도 Codex도 쓸 때마다 승인을 요청합니다 [문서]. 위치는 S6에서 정합니다.

## 2. 실측 (프로세스가 시작 신호에 맞춰 동시에 기록, 10%는 10 KB·나머지는 1 KB) [실측]

| 방식 | 8개 × 500건 | 16개 × 300건 | 걸린 시간 (8개) |
| --- | --- | --- | --- |
| overwrite (읽고 고쳐 통째로 저장 = 지금의 CURRENT.md 편집) | **2,172/4,000 손실 (54%)** | **1,725/4,800 손실 (36%)** | 17.1 s, 저장 충돌 재시도 11,958회 |
| append_nolock (같은 jsonl, 잠금 없음) | **924건 손실, 깨진 줄 139** | **730건 손실, 깨진 줄 240** | 0.56 s |
| append_lock (같은 jsonl, 잠금 파일) | 손실 0, 깨진 줄 0 | 손실 0, 깨진 줄 0 | 1.59 s |
| per_writer (프로세스마다 자기 jsonl) | 손실 0 | 손실 0 | 0.79 s |
| sqlite (WAL, 건마다 트랜잭션) | 손실 0 | 손실 0 | 7.81 s |

- 잠금을 잡은 프로세스를 강제 종료하면 잠금이 곧바로 풀렸습니다. 3회 모두 0.03 ms 안이었습니다 [실측]. 세션이 죽어도 잠금이 남아 막히지 않습니다.
  - **정정 (2026-10-18, Pro P1·P2 지적)**: 이 시험의 타이머는 `p.kill(); p.wait()`로 종료를 확인한 **뒤에** 시작했습니다. 그래서 0.03 ms는 "강제 종료부터 잠금이 풀리기까지 걸린 시간"이 아닙니다. 맞는 표현은 "종료를 확인한 뒤 잠금을 곧바로 다시 얻었다(3회)"입니다. Windows 문서는 해제 시간이 자원 상태에 따라 달라질 수 있다고 설명합니다.
  - 이 문서의 "손실 0"이 뜻하는 범위도 줄입니다. 이 시험에서 확인한 것은 "예상한 (w,i) 기록이 빠지지 않았다"뿐입니다. 성공한 기록이 장애 뒤에도 남는지(fsync 없음), 오래된 CURRENT를 바탕으로 한 덮어쓰기 충돌은 시험하지 않았습니다.
  - 시험에 쓴 SQLite 3.50.4는 공식 문서상 WAL-reset 버그의 영향 범위(3.7.0–3.51.2)에 들어갑니다. 수정판은 3.50.7과 3.51.3 이상입니다.
- 실제 사례 [실측]: 2026-10-17 18:20, 이 작업대 CURRENT.md를 두 세션(MEM_STRG·BTSR)이 고쳐 써서 한 줄이 되돌아갔습니다. 위 overwrite 행과 같은 현상입니다.
- 원자료: [p8](s2_results_p8_20261017.json) · [p16](s2_results_p16_20261017.json) · [kill](s2_results_kill_20261017.json)

## 3. 왜 잠금 없는 추가가 깨지나 [판단, 원인 미실측]

- 파이썬의 추가 모드는 Windows에서 "끝으로 이동 → 쓰기" 두 단계로 동작하는 것으로 보입니다. 두 프로세스가 같은 끝 위치에 쓰면 한쪽이 덮어써집니다.
- 10 KB 기록은 버퍼(8 KB)를 넘어 여러 번에 나눠 쓰이므로 중간에 남의 기록이 끼어듭니다(깨진 줄).
- 원인 분석은 이번 범위가 아닙니다. 결과만 근거로 씁니다.

## 4. 권고 쓰기 규칙 (B안 보강) [판단]

1. 스트림은 역할마다 하나(`<role>.jsonl`)입니다. 작업대당 작성 세션은 1개이므로(설계 §3.2) 평소에는 경합이 거의 없습니다.
2. 그래도 오늘 같은 사고를 막기 위해 쓰기마다 `<role>.jsonl.lock`을 잡습니다. 잠금 파일은 지우지 않습니다.
   - Windows 잠금은 강제 방식이라 데이터 파일 자체를 잠그면 읽기도 막힙니다. 그래서 잠금은 별도 파일에 겁니다.
3. 쓰기는 CLI 하나로만 합니다(D15와 같은 원칙). 사람·에이전트가 스트림을 직접 고치지 않습니다.
4. 기록마다 `created_by`(세션 이름)를 남깁니다. 역할 주인이 아닌 세션이 쓴 기록은 막지 않고, verify에서 표시합니다.
5. 끝줄이 줄바꿈 없이 끝나면(쓰는 도중 중단) 투영에서 제외하고 보고합니다. CLI는 다음 기록을 새 줄에서 시작합니다. 이 항목은 설계만 했고 실측하지 않았습니다.
6. SQLite는 투영(캐시)으로만 씁니다. 동시성은 SQLite도 문제없지만, S1에서 본 백업·동기화 단점이 남습니다.

## 5. 세션 권한 — 저장소 위치의 제약 [문서]

| 실행기 | 작업 폴더 밖 쓰기 | 근거 |
| --- | --- | --- |
| Claude Code (데스크톱 포함) | 파일 수정은 승인을 요청합니다. acceptEdits도 작업 폴더나 `additionalDirectories` 안만 자동 승인합니다 | code.claude.com/docs/en/permissions |
| Codex (workspace-write) | 작업 공간 안만 씁니다. 밖은 on-request 승인이 필요하고, 넓히려면 `sandbox_workspace_write.writable_roots`를 씁니다. Windows는 자체 샌드박스를 씁니다 | learn.chatgpt.com/docs/sandboxing |

- 이것이 뜻하는 것: 저장소를 각 세션 작업 폴더 밖 고정 경로에 두면 매번 승인하거나 설정을 바꿔야 합니다. 설정 변경은 Owner가 결정합니다.
- 반대로 저장소 폴더 안에 Git 제외로 두면, worktree 사본마다 저장소가 따로 생겨 메모가 갈라질 위험이 있습니다. RHS 사본이 20개입니다. 이 부분은 실측하지 않았습니다 [미확인].
- 둘 다 S6(위치·여러 기기)에서 정합니다.
- 실제 데스크톱 세션에서 승인 요청이 뜨는지는 아직 실측하지 않았습니다 [미확인]. Codex 쪽 실측은 범위 밖이라 Codex 세션 몫입니다.
