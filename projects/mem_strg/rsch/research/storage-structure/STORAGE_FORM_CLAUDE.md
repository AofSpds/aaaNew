# S1 저장 형태 — 파일 / jsonl+SQLite 투영 / SQLite 단독

- 작성: 2026-10-17, AAA/NEW/RSCH/MEM_STRG · REQ-001 S1
- 실측 환경: HANAL, Windows 11, Python 3.13.14, SQLite 3.50.4, git 2.55.0
- 스크립트: [s1_form_bench.py](s1_form_bench.py) (표준 라이브러리 + git만 씀, 지우는 동작 없음)

> **정정 (2026-10-18, Pro P1·P2 검토 → [REVIEW](../../reviews/STORAGE_ENGINE_OPERATIONS_REVIEW_CLAUDE.md) #3–#6)**
> - 쓰기 시간 비교는 내구성이 같은 조건이 아닙니다. jsonl은 fsync를 하지 않았고, SQLite는 synchronous=NORMAL이었습니다. B의 SQLite 투영 비용도 쓰기 시간에 들어 있지 않습니다. 그래서 "속도는 판단 기준이 아니다"라는 결론은 유지하되, 0.24 대 0.06 ms를 같은 조건의 비교로 읽으면 안 됩니다.
> - §4의 "C: 백업 전에 checkpoint가 필요합니다"는 일반 명제로는 틀립니다. 실행 중인 DB의 일관된 사본을 만드는 공식 경로는 backup API와 `VACUUM INTO`입니다.
> - jsonl의 Git 백업 장점은 **읽을 수 있는 추가 diff**입니다. 크기는 gc 뒤 SQLite가 더 작았습니다(2,007 vs 3,235 KiB, §3 표).
> - 실측에 쓴 SQLite 3.50.4는 WAL-reset 버그 범위(3.7.0–3.51.2) 안입니다. 수정판은 3.50.7과 3.51.3 이상입니다 [문서, sqlite.org/wal.html §11].
> - 빠진 대조군: "SQLite 정본 + PR 때 결정적인 jsonl export". 다음 실측에 넣습니다.

## 1. 결론

권고 후보는 **B: 역할별 jsonl 추가 전용 + SQLite 투영(재생성 캐시) + 생성 MD view**입니다. 확정은 S2(동시 쓰기) 실측 뒤에 합니다.
- 세 형태 모두 속도는 충분해서 판단 기준이 되지 않습니다 [실측].
- 차이를 만드는 것은 파일 수, Git 백업 모양, 덮어쓰기 손실, 동기화 위험입니다.

## 2. 요구 (원천: REQ-001, RHS STRUCTURE_DECISIONS #29–#39)

- Current는 덮어쓰고, 지난 판은 아카이브에 쌓으며, 아무것도 지우지 않습니다(#1·#30).
- 역할 Current를 모아 도메인 Current를 만듭니다(#33).
- Git에는 참조값만 두고, 로컬 저장소는 PR마다 백업합니다(#36·#37).
- 여러 세션이 쓸 수 있어야 하고, 외부 서비스는 쓰지 않습니다.

## 3. 실측 (갱신 10,000건 = 역할 20개 × 평균 500건, 백업 5회) [실측]

| | A 파일 (CURRENT 덮어쓰기 + archive 사본) | B jsonl + SQLite 투영 | C SQLite 단독 (WAL) |
| --- | --- | --- | --- |
| 쓰기 1건 | 6.42 ms | 0.24 ms | 0.06 ms |
| 파일 수 | **10,022** | 42 | 25 |
| 디스크 | 12.5 MB | 12.3 MB | 14.0 MB |
| 롤업(도메인 Current) 최대 | 125 ms | 204 ms (투영 전체 재생성) | 21 ms |
| 백업 1회(갱신 2,000건)의 Git 변경 | 파일 2,041개, +44,291/−291줄 | 파일 20개, +2,000/−0줄 (추가만) | 바이너리 1개 (줄 diff 없음) |

- 1만 건은 하루 100건이면 100일 분량입니다. 다만 하루 갱신 수는 가정입니다 [미확인].
- A와 B의 롤업 결과는 같습니다. 스모크 실행에서 표 내용을 비교했습니다 [실측].

문서 근거:
- sqlite.org/wal.html: "WAL does not work over a network filesystem". WAL 파일을 DB와 떼어 놓으면 커밋된 트랜잭션을 잃을 수 있습니다.
- sqlite.org/howtocorrupt.html §1.2: 트랜잭션 도중 백업하면 손상됩니다. 안전한 방법은 `VACUUM INTO`나 backup API입니다. 클라우드 동기화 서비스를 직접 언급하지는 않습니다.

## 5. 관계 엔진 memory-store와 합칠지 [판단]

**저장소는 따로 두고, 봉투 규칙은 같게** 하기를 권고합니다.
- 메모를 따로 두는 이유: memory-store jsonl은 Git이 추적합니다(D8 위치, D15 `merge=union`). 메모는 "Git에는 참조값만" 원칙(#36)을 따르므로 Git 밖에 있어야 합니다.
- 수명도 다릅니다. 메모는 자주 덮어쓰는 현재 상태이고, 엔진 기록은 검토와 권한이 필요합니다(D4·D5).
- 함께 쓸 규칙: D14 ULID, D17 정규화(UTF-8·NFC·LF·sort_keys), D20 상대 경로·`sensitivity`, D15 단일 쓰기 CLI.
- 이렇게 맞춰 두면 나중에 memory-engine이 메모 스트림을 source_rev로 단방향 가져올 수 있습니다.
