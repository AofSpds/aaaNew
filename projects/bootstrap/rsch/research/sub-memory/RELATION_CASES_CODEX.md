## 기억 한 항목의 범위

비교 단위는 독립적으로 적용하거나 검토할 수 있는 주장·규칙·상태 하나로 제안한다. 문단 전체를 하나로 묶으면 겹치는 교훈과 고유한 실패 근거를 함께 지울 수 있다. 반대로 문장을 너무 잘게 나누어 적용 조건을 잃어서도 안 된다.

각 항목에는 다음 정보를 연결한다. 이것은 논리적인 요구이며 저장 제품이나 DB 스키마 선택은 아니다.

- 내용과 종류: 사용자 지시, 관측 결과, 교훈 후보, 현재 진행 상태 등.
- 적용 범위: 프로젝트·역할·업무·용도와 예외 조건. 모르는 값은 모름으로 남긴다.
- 적용 시점과 사건 순서: 당시 상태인지 현재 규칙인지, 어떤 지시 이후에 바뀌었는지.
- 근거: 원문 위치·버전과 작성 주체. 에이전트가 재구성한 내용과 원문을 구분한다.
- 확인 수준: 문서 읽기, 실행 관측, 독립 재현, 재사용 효과와 검토 상태.

## 사례 1 겹치는 교훈과 고유한 근거

근거는 [LESSONS_CODEX.md](../../memory/codex-rsch/LESSONS_CODEX.md)의 표 첫 행 7행과 “시작 위치를 인수하는 경험” 15행이다.

- A 원문: “첫 작업에서 역할과 절대 작업대 경로를 확인하고, 파일 명령에 명시한다.”
- B 원문: “사용자 지정 역할·절대 경로·현재 과제·메모 진입점을 먼저 대조한다.”

겹치는 주장 후보는 “업무 시작 시 사용자 지정 역할과 절대 작업대 경로를 확인한다”다. A에는 파일 명령에 경로를 명시한다는 내용이, B에는 과제와 메모 진입점을 확인한다는 내용이 더 있다. A가 포함된 표에는 실제 혼동·사용자 재설명·자동 강제 미구현이라는 근거도 있다.

**기대 처리:** 공통 주장에 두 출처를 연결하고 추가 내용은 각각 보존한다. 문장 전체의 완전 중복으로 판정하지 않는다. 같은 경험을 두 번 적은 사실을 독립된 성공 증거 두 건으로 세지 않는다.

**확인과 보류:** 기억 관리부는 병합 확정 전에 적용 범위와 빠질 내용을 비교한다. 고유한 조건·근거·확인 수준이 사라지면 전체 병합을 보류한다. 공통 주장을 연결하더라도 원문의 “교훈 후보” 상태를 검토 완료로 올리지 않는다.

**충돌 시험용 변형:** 두 경로를 동일 역할·동일 연구 산출물·겹치는 적용 기간에 대한 유일한 위치 지정으로 바꾸고, 변경 지시도 없다고 가정하면 양립할 수 없는 충돌 후보다. 이는 실제 사용자 지시가 아닌 평가용 변형이다. 기억 관리부는 충돌을 기록하고, 근거 있는 해결 전까지 한쪽을 유일한 현재값으로 확정하지 않아야 한다. 업무 전체 중단 여부는 별도 실행 정책이다.

## 사례 3 사용자 지시 이후의 현재 상태 갱신

A는 [INTAKE_CODEX.md](INTAKE_CODEX.md) 3·26행의 “이번 단계는 인수만 수행했다”, “실제 jevlike 구현 조사는 아직 시작하지 않았다”다. 최초 인수 당시를 설명하는 기록이다.

이후 이 채팅에서 사용자가 “요구사항을 확인하고 정리하며 추가 리써치를 통해 정교한 요구사항으로 다듬겠습니다”, 이어 “Jevlike도 연구사항에 포함됩니다”라고 지시했다. 그 뒤 공개 구현의 문서·소스를 확인하여 [1차 정교화 초안](R05_R06_REFINEMENT_CODEX.md)에 기록했다.

**기대 처리:** 현재 진행 상태는 “요구사항 정교화 및 공개 jevlike 후보의 문서·소스 조사에 착수”로 갱신한다. A는 당시 상태로 보존한다. 새 지시는 연구 범위의 근거이고, 결과 파일과 실제 읽기 기록은 조사 수행의 근거다. 새 지시만으로 조사 완료를 선언하지 않는다.

**확인과 보류:** 도메인의 상태 갱신부는 대상 세션·변경 범위·사용자 지시의 순서·수행 근거를 확인한다. 문서 수정 시각만으로 대체를 정하지 않는다. 지시나 수행 근거가 빠지면 해당 상태 갱신을 보류한다. 인수 당시 기록과 이후 상태를 동일 시점의 상충 주장으로 취급하지 않는다.

이 사례는 현재 상태의 갱신이다. 재사용할 교훈의 폐기나 검토 완료를 뜻하지 않는다. 부모 파일 갱신이나 설치·제품 변경의 권한도 이 상태 변경에서 파생시키지 않는다.

## 요구사항에 추가할 구체적인 조건

1. **M01 항목 분리:** 교훈·상태·근거를 구분하되 연결을 유지한다. 일부 중복으로 문단 전체를 삭제하거나 확인 수준을 높이지 않는다.
2. **M02 의미 관계:** 같은 범위·같은 적용 시점인지 확인한 뒤 중복·보완·충돌을 판단한다. 비교 조건 부족은 “무관”이나 “충돌”로 강제 분류하지 않는다.
3. **M03 판정 입력:** 모델에 전달할 두 항목의 조건·근거 요약·확인 수준이 보존되었는지 검사한다. 필요한 내용이 잘렸다면 해당 점수를 확정 처리에 사용하지 않는다.
4. **M04 변경 결정:** 의미 관계와 처리 결정을 구분한다. 관계가 충돌한다는 판정만으로 어느 쪽을 대체할지 정할 수 없다. 대체에는 방향·적용 범위·지시 또는 검토 근거가 필요하다.

jevlike에 제시할 관계 후보는 일부가 동시에 성립할 수 있다. “부분 중복과 보완”처럼 겹치는 경우와 “판단 보류”를 어떻게 표현할지 평가 입력에서 검토한다. 이 초안의 판정을 검토 없이 학습 정답으로 사용하지 않는다.

## 첫 평가 입력의 사전 확인

[첫 입력 초안](JEVLIKE_CASE_01_DRAFT.json)은 사례 2의 실제 기록을 문맥으로 재구성한다. 입력에는 A·B의 프로젝트·역할·용도·작업대를 넣고, 기대 판정 설명은 입력 밖에 둔다. 이 사례의 선택지는 중복 / 충돌 / 역할별 공존 / 판단 보류다. 기대 결과는 “역할별 공존”이며, 모델 출력이나 독립 검토된 정답이 아니다.

로컬 UTF-8 길이 계산과 192바이트 앞부분 확인을 수행했다. 기본 길이에서 자르면 두 번째 기록의 역할을 보존하지 못한다. 따라서 모델 호출 전에 두 기록의 조건 보존을 확인하고, 손실이 있으면 입력을 다시 구성하거나 지원 가능한 설정을 검토하도록 제안한다. 단순히 기본값 숫자를 늘리면 기존 모델이 지원한다고 가정하지 않는다. 이번에는 모델 실행이나 설정 변경을 하지 않았다.

처음 작성한 긴 선택지 중 “정보 부족으로 판단 보류”도 33바이트여서 문서상 기본 32바이트를 넘었다. 최종 후보 문구는 짧게 고쳤고, 각 문구의 길이는 입력 초안에 남겼다. 문맥과 선택지 양쪽의 길이를 확인해야 한다.
