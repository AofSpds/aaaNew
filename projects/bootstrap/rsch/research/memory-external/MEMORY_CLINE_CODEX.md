# Cline Memory Bank와 역할 작업대의 기억

2026-10-14 공식 문서 기준. 약 2페이지 분량의 첫 사례다.

**첫 번째 페이지 — 무엇을 저장하고 어떻게 이어받는가**

Cline의 Memory Bank는 프로젝트 안에 Markdown으로 작업 맥락을 남기고, 다음 작업에서 다시 읽도록 운영하는 방식이다. 공식 예시는 목적, 현재 상황, 설계·기술 맥락, 진행 상태를 나눠 저장한다. 특히 activeContext.md에는 현재 초점과 다음 단계를, progress.md에는 완료·미완료 상태를 기록한다. 중요한 변경이나 방향 전환 뒤에 갱신하고, 새 대화에서 읽도록 지시한다. [공식 Memory Bank 설명](https://docs.cline.bot/best-practices/memory-bank)

우리 상황에 대입하면 “bootstrap은 무엇을 만드는 프로젝트인가”, “나는 rsch인가 pln인가”, “어디에 기록해야 하는가”, “이미 끝난 조사는 무엇인가”를 대화 밖에서도 찾을 수 있게 하는 것이다. 세션이 바뀌어도 유지할 내용과 매번 바뀌는 진행 상태를 구분하면, 다음 에이전트가 읽어야 할 내용을 정하기가 쉬워진다.

예를 들어 이번 Claude 조사 완료를 처리한다면, 완료 통보와 결과 파일을 근거로 현재 상태를 바꾸고, 남은 질문만 다음 단계로 남긴다. 다음 세션은 완료된 조사를 다시 맡기기 전에 이 상태를 읽을 수 있다. 사용자가 “그건 이미 했잖아요”라고 설명하는 비용을 줄이는 것이 기대 효과다.

여기에는 두 가지 파일의 역할이 있다. 하나는 “어디를 읽고 언제 갱신할 것인가”라는 운영 지침이고, 다른 하나는 실제로 쌓이는 작업 기억이다. Cline은 프로젝트의 .clinerules 같은 규칙 디렉터리에서 지침을 읽는다. 규칙은 문맥으로 전달되며, 파일 경로에 따라 조건부로 활성화할 수도 있다. [공식 Rules 설명](https://docs.cline.bot/customization/cline-rules)

이 구분을 우리에게 적용하면, 매번 넣을 짧은 지침은 “너의 작업대는 rsch이며 시작할 때 이 진입점을 읽어라”가 된다. 읽게 될 진입점에는 현재 업무와 필요한 경험의 위치를 둔다. 조사 보고서 전체나 설치 이력 전체를 항상 전달할 필요는 없다.

다만 “기억을 읽으라는 지침이 들어갔다”와 “기억 내용을 읽었다”는 다르다. 우리도 README를 만들어 놓았지만, Claude 완료 상태를 갱신하지 않았다. 그 상태에서는 읽기에 성공해도 오래된 정보를 인수한다. 따라서 읽는 연결과 쓰는 시점이 함께 맞아야 한다.

우리 요구에서 한 단계 더 필요한 것은 시작 위치다. 기억에 rsch 경로를 써 두는 것만으로 실행기의 cwd가 변경되지는 않는다. 도메인이 세션을 시작할 때 작업대를 지정하고, 그 작업대에 맞는 기억 진입점을 전달해야 한다. Memory Bank는 이때 전달할 내용을 정리하는 방법으로 참고할 수 있다.

**두 번째 페이지 — 우리의 시행착오를 어떻게 경험으로 바꿀 것인가**

현재 rsch에 적용할 때는 기존 파일로 먼저 시작할 수 있다. README에는 현재 상태와 읽을 곳을, 조사 결과에는 근거와 결론을, LESSONS_CODEX.md에는 실패와 다음에 적용할 교훈을 둔다. 다음 구분은 Cline의 고정 규격이 아니라 우리 작업에 맞춘 제안이다.

| 남길 내용 | 이번 사례 | 다음 업무에서의 용도 |
|---|---|---|
| 작업 기록 | Claude가 진입 조사를 완료했다. 결과 파일을 확인했다. | 실제로 무엇이 있었는지 확인한다. |
| 현재 상태 | 조사 완료. 독립 재현은 미실시. | 이미 한 일과 남은 일을 구분한다. |
| 경험 후보 | 완료 통보 수신 때 현재 상태와 산출물 링크를 함께 갱신한다. | 비슷한 인계 누락을 예방한다. |

“오늘 경로를 잘못 잡았다”만 저장하면 다음 에이전트가 상황을 다시 해석해야 한다. 경험으로 쓰려면 “도구의 기본 cwd를 역할 작업대로 추정하지 말고, 지정된 절대 경로를 확인한다”까지 정리해야 한다. 여기에 적용 조건인 “여러 프로젝트나 역할을 오가는 작업”을 붙이면 불필요한 곳에 규칙을 적용하는 일도 줄일 수 있다.

이것이 말씀하신 역할별 경험 view로 발전할 수 있는 지점이다. 예를 들어 rsch의 view에는 조사 근거를 고정하는 법, 문서 주장과 실측을 구분하는 법, 완료 결과를 인계하는 법이 들어갈 수 있다. pln에는 조사 결과를 계획의 결정과 미확인 사항으로 옮기는 경험이 필요할 수 있다. 같은 대화 전체를 역할마다 복제하기보다 역할에 필요한 교훈을 골라 제공하는 구상이다.

리뷰는 여기서 교훈의 범위를 조정한다. “모든 보고를 믿지 말라”는 지나치게 넓고 비용이 큰 규칙이다. 이번 경험으로는 “담당자의 실측 보고와 내가 독립 확인한 범위를 구분해 기록하라”가 더 정확하다. 그러면 결과를 활용하면서도 검증 수준을 과장하지 않을 수 있다.

Git은 이 파일들이 언제 어떻게 바뀌었는지 남기는 데 쓸 수 있다. 잘못 정리한 교훈을 되돌리거나, 현재 상태가 어떤 근거로 변경됐는지 검토하기에도 유용하다. 다만 기록할 항목을 고르고 최신 상태로 고치는 업무는 여전히 필요하다. 커밋 성공만으로 기억이 정확하거나 다음 모델이 읽었다고 판단할 수는 없다.

또한 문서에 “반드시 읽어라”라고 쓰는 것은 강제 실행 장치와 구분해야 한다. 우리에게 첫 작업 전 인수 확인이 꼭 필요하다면, 도메인 측에서 역할·작업대·기억 버전을 전달하고 확인 결과를 받는 절차를 별도로 설계해야 한다. 그 절차가 빠졌을 때 실행을 막을지는 실행환경의 통제 지점과 연결해서 판단할 문제다.

이번 사례에서 먼저 시험할 것은 작다. 새 세션이 진입점 하나를 받아 다음 세 가지를 정확하게 인수하는지 보면 된다.

1. 작업대가 bootstrap 아래 rsch라는 것.
2. 작업 기억의 위치와 Claude 조사의 완료 상태.
3. 현재 목적이 역할 경험을 다음 작업에 재사용하는 구조를 연구하는 것.

이 세 가지를 재설명하지 않아도 되고, 이미 끝난 조사를 반복하지 않는다면 첫 연결이 작동한 것이다. 이후 실제 업무에서 같은 정정이 줄어드는지 봐야 한다. 사용자에게 필요한 효용은 그때부터 확인할 수 있다.
